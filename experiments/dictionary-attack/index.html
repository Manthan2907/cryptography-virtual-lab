Dictionary Attack

Simulate a dictionary attack by testing a predefined set of candidate passwords against a stored SHA-256 password hash.

Theory

1. What is a Dictionary Attack?

A dictionary attack is a password-guessing technique that tests a prepared list of likely passwords against a protected password representation. It focuses on words and patterns that people commonly choose.

Systems should store password hashes rather than plaintext passwords. A hash is a one-way representation, but someone who obtains a stored hash can hash guesses and compare their results with it.

2. How Does a Dictionary Attack Work?

This simulation tries its predefined candidates in order: admin, 123456, password, qwerty, and letmein. It hashes each candidate and compares the result with the target hash. It stops at the first match; if all five candidates fail, it reports that no match was found in this dictionary.

Example when the target password is qwerty:

  1. Calculate SHA-256("admin"); compare it with the target hash. It does not match.
  2. Repeat for 123456 and password; neither matches.
  3. Calculate SHA-256("qwerty"); it matches the target hash, so the simulation reports the candidate and stops.
3. Role of SHA-256 Hashing

SHA-256 is a cryptographic hash function that produces a deterministic 256-bit digest (usually displayed as 64 hexadecimal characters). The same input produces the same digest, which lets the simulation compare a candidate's digest with the target digest. Hashing is not encryption and does not provide a decryption operation.

This experiment uses plain SHA-256 to demonstrate comparison. Plain SHA-256 is designed to be fast, so it is not suitable by itself for storing real passwords.

4. Dictionary Attack vs Brute Force Attack

A dictionary attack tries a prepared set of likely words and patterns. A brute-force attack systematically tries combinations from a defined character set. Dictionary attacks can find common or reused passwords quickly when they appear in the list; brute force can cover passwords absent from that list, but the number of combinations can grow rapidly with password length and character variety.

5. Limitations of Dictionary Attacks

Success depends on whether the password or a likely variation is included in the candidates. This simulation has only five candidates, so a failure means only that none of those five matched; it does not prove that a password is secure. A stolen hash, the hashing method, salts, and available computing resources also affect real-world risk.

6. Prevention Techniques
  • Use long, unique passwords or passphrases that are not based on common words or predictable patterns.
  • Store passwords with a dedicated, deliberately slow password-hashing scheme such as Argon2id, bcrypt, scrypt, or PBKDF2, configured appropriately and with a unique salt per password.
  • Use multi-factor authentication to add a second verification factor.
  • For online login systems, rate-limit repeated attempts and monitor suspicious activity.

Rate limiting helps protect online login endpoints; it cannot slow guesses made offline against a hash that has already been obtained. Slow password hashing and unique salts help defend stored credentials in that situation.

Procedure

Steps opened: 0 of 8

  1. 1. Open the Simulation tab

    Select Simulation in the experiment navigation to access the target-password and attack controls.

  2. 2. Enter a target password

    Type a password into the target-password field. It will be hashed locally when you generate the target hash; changing it clears any previously generated target hash.

  3. 3. Generate the target hash

    Select Generate Target Hash. The simulation uses the Web Crypto API to create and display the password's SHA-256 hash. A non-empty target password is required.

  4. 4. Start the dictionary attack

    Select Start Attack. This control is enabled after a valid target hash has been generated.

  5. 5. Observe the candidate sequence

    The simulation tests admin, 123456, password, qwerty, and letmein, in that order, hashing one candidate at a time with a 600 ms pause after each non-match.

  6. 6. Observe each comparison

    For each attempt, check the current candidate, attempt count, progress bar, and attack log. The log shows the candidate's SHA-256 digest and whether it matched the target.

  7. 7. Review the result

    If a candidate matches, the attack stops and reports that a password was found. If all five candidates are tested without a match, it reports that the target was not present in this predefined dictionary.

  8. 8. Reset the simulation

    Select Reset to stop any running attack and clear the password, target hash, progress, attempt count, log, and result before another experiment.

Access Control List (ACL)

Implement an Access Control List and demonstrate authorization based on assigned permissions.

Aim & Objectives

Aim: To study and simulate an Access Control List (ACL) mechanism, demonstrating how modern operating systems determine whether a subject is authorized to perform specific operations on a secured resource within a System Security framework.

Objectives:

  • Understand the foundational concept of Discretionary Access Control (DAC) as a core pillar of Operating System Security.
  • Analyze how core permission attributes (Read, Write, Execute) enforce Confidentiality and Integrity of sensitive data.
  • Examine the sequential rule-evaluation process that operating systems use to process access requests securely.
  • Configure Access Control Entries (ACEs) and observe real-time authorization decisions to prevent unauthorized privilege escalation.

Theory

1. File Access Control Concepts & Entity Roles

In a secured operating system, every file has an owner, and access is rigorously controlled through users, groups, and permissions. Understanding the distinction between entity roles is critical for preventing unauthorized data exposure:

Category Meaning & Security Function
Owner The user who currently owns the file and holds primary administrative authority to configure its access rules and permissions.
Creator The user who originally created the file; may or may not remain its owner if ownership is reassigned by administrators.
Group A collection of users sharing permissions (e.g., comp_eng department, devs, hr).
User An individual account requesting access to the file.
Others Users outside the owner and group categories (World / Public).
Realistic Example: Rahul creates secret.txt. Initially, Rahul is both the Creator and Owner. If a system administrator transfers administrative control of department files to Alice (via chown alice secret.txt), Alice becomes the Owner (controlling access policies), while Rahul remains the original Creator. The system evaluates Alice's policies to determine access.

2. The Top-Down Approach (↓)

In the top-down approach, access permissions are determined from a higher-level authority or parent directory downward toward the files and users beneath it:

Level 1: Owner / Administrator

Controls top-level access policies, organizational boundaries, and sets directory-level default access rules.

↓

Level 2: Group (Department / Team)

Shared permissions applied across members of a functional group (e.g., members of the Computer Engineering group).

↓

Level 3: Users / Files

Child files inherit permissions from parent directories; users access files strictly according to applicable inherited or explicit rules.

Departmental Example: An administrator sets a department directory (/departments/comp_eng/) so that all members of the Computer Engineering group can read its files. Individual child files (such as secret.txt and lab_manual.c) automatically inherit those permissions if the operating system supports inheritance (POSIX Default ACLs).

3. Directory Default ACLs & Permission Inheritance

In modern POSIX file systems, directories support Default ACLs (specified with the default: prefix). When an administrator configures a default ACL on a folder (e.g., default:group:comp_eng:r-x):

  • Downward Inheritance: Any new file created inside inherits the default rules automatically without manual intervention.
  • Explicit File Overrides: A file can still declare explicit file-level ACEs. Explicit rules take precedence over inherited directory defaults if both match the same subject.
  • Isolation Control: If inheritance is disabled on a file, it operates solely on its local explicit ACEs and base permissions.

4. Core Permissions & The ACL Mask

When a user or group is listed in an ACL, standard POSIX environments assign three primary privileges:

  • Read (r) - Confidentiality: Ability to view file content. Prevents unauthorized data disclosure.
  • Write (w) - Integrity: Ability to alter or delete content. Protects data from tampering.
  • Execute (x) - System Safety: Ability to execute program or traverse directories.

The ACL Mask: Acts as a maximum allowed ceiling filtering permissions for Named Users and Groups. It does not restrict the File Owner or Other (World).

Sequential Precedence Evaluation Process (↓)

When a user attempts to access a protected file, the authorization engine evaluates the top-down hierarchy and ACL entries sequentially, stopping as soon as a definitive match is reached:

0. Superuser (Root) Bypass

The system first checks if the user is root. Root automatically receives full Read and Write access, and receives Execute if at least one execute bit exists on the file.

1. Resource Owner Match

Checks if the user matches the file's current Owner. If true, the Owner's permissions are applied (Creator is logged in metadata). Evaluation stops here.

2. Explicit Named User Entries

Checks for an explicit User ACE matching the subject (explicit file rule takes precedence over inherited directory rule). Permissions are filtered by the ACL Mask.

3. Group Memberships Union (Explicit + Inherited)

Combines all matching group rules (owning group, explicit file group entries, and inherited directory default group entries). The union is filtered by the ACL Mask.

4. Other (World) Permissions / Default Deny

If no user or group matches occur, the system applies "Other" permissions. If the requested operation is not explicitly granted, access is Denied.

Procedure

Follow these structured steps to explore the Top-Down Approach and ACL authorization engine:

1 Manage System Users & Departments

In the Simulation tab, review or add operating system users and their departmental groups using the System User Manager (e.g., User rahul in comp_eng, alice in admins, comp_eng, hr).

2 Select Resource in Directory Hierarchy

Choose a target file grouped under a parent directory (e.g., /departments/comp_eng/secret.txt created by Rahul, or /finance/payroll.csv).

3 Inspect Roles & Authority Metadata

Observe the Resource Metadata card displaying the Parent Directory (Authority), Creator (who made the file), Current Owner (who controls the ACL), and Owning Group.

4 Test Top-Down Directory Inheritance

Toggle the "Enable Top-Down Inheritance" switch. Watch how the directory default ACE (e.g., comp_eng:r-x) dynamically propagates down to the file's active ACL table with an Inherited (Dir Default) badge.

5 Add Explicit File Overrides & ACL Mask

Use the ACL Rule Editor to add explicit file-level ACEs or an ACL Mask. Observe how explicit file rules override inherited defaults and how the mask restricts effective rights.

6 Simulate Access Request & Inspect Trace

Select a requesting user (e.g., rahul or charlie) and an operation (Read, Write, or Execute). Click "Evaluate Access Request" and study the 3-phase execution trace explaining the Top-Down decision.

Knowledge Assessment (10 Questions)

Test your comprehensive understanding of Access Control Lists, the Top-Down Approach, Entity Roles, and Precedence.

1. Conceptually, what is an Access Control List (ACL) in an operating system?

2. In file access control concepts, what is the primary distinction between a "Creator" and an "Owner"?

3. In the Top-Down Approach (↓) to file access control, how are permissions determined?

4. User Bob belongs to the "devs" group. A file grants Write access to "devs". However, there is also an explicit Named User ACE specifically for "Bob" giving him ONLY Read access. What access will Bob have?

5. When an administrator configures Default ACLs on directory /departments/comp_eng/, how do child files behave?

6. What is the primary function of the POSIX ACL Mask (mask::) entry on a secured file?

7. User Charlie belongs to two groups: "devs" (granted Read r--) and "hr" (granted Write -w-) on a file. Charlie has no named user ACE. What effective permission does Charlie receive?

8. How does standard POSIX DAC evaluate an access request initiated by the root (superuser) account?

9. When does the authorization engine fall back to applying the "Other" (World) permissions?

10. Why is the Principle of Least Privilege (PoLP) a fundamental guideline when configuring Access Control Lists?

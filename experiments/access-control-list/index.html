Access Control List (ACL)

Implement an Access Control List and demonstrate authorization based on assigned permissions.

Aim & Objectives

Aim: To study and simulate an Access Control List (ACL) mechanism, demonstrating how modern operating systems determine whether a subject is authorized to perform specific operations on a secured resource within a System Security framework.

Objectives:

  • Understand the foundational concept of Discretionary Access Control (DAC) as a core pillar of Operating System Security.
  • Analyze how core permission attributes (Read, Write, Execute) enforce Confidentiality and Integrity of sensitive data.
  • Examine the sequential rule-evaluation process that operating systems use to process access requests securely.
  • Configure Access Control Entries (ACEs) and observe real-time authorization decisions to prevent unauthorized privilege escalation.

Theory

Introduction to Access Control Lists

In the context of Cryptography and System Security, simply encrypting data is not always sufficient; the system must also tightly control who can access the cryptographic keys and protected resources. An Access Control List (ACL) is a fundamental security mechanism used by operating systems to manage these permissions. Conceptually, it is an authorized registry attached directly to a resource. This registry contains individual rules, known as Access Control Entries (ACEs), which specify exactly which users or groups are granted or denied access.

Core Permissions for Confidentiality & Integrity

When a user is listed in an ACL, the system assigns them specific privileges. In standard POSIX environments, these privileges map directly to core security principles:

  • Read (r) - Confidentiality: Grants the ability to open or view the file. Restricting this prevents unauthorized disclosure of sensitive data.
  • Write (w) - Integrity: Grants the ability to modify or delete the file's contents. Restricting this prevents unauthorized tampering or data corruption.
  • Execute (x) - System Safety: Grants the ability to run the file as a program. Restricting this prevents the execution of untrusted or malicious scripts.

The ACL Mask & System Users

System Users vs. File Rules: Creating a user in the OS and assigning them to groups (System User Management) is separate from granting them file permissions. A user only gains access if the file's ACL references them or their groups.

The ACL Mask: The mask acts as a maximum allowed ceiling for permissions. It filters permissions for Named Users and Groups, but does not restrict the File Owner or Other (World). For example, if a user's ACE grants rwx but the mask is r--, their effective permission is reduced to r--.

The Sequential Evaluation Process

When a user attempts to access a protected file, the authorization engine processes the ACL in a strict, sequential order. The engine stops evaluating as soon as it finds a definitive match:

0. Superuser (Root) Bypass

The system first checks if the user is root. Root automatically receives full Read and Write access, and receives Execute if at least one execute bit exists on the file. Evaluation stops here.

1. Resource Owner

The system checks if the user is the owner of the file. If true, the owner's specific permissions are applied, and evaluation stops.

2. Explicit User Entries

If the user is not the owner, the system looks for an ACE that explicitly names the user. If found, those permissions (capped by the ACL Mask) are applied, and evaluation stops.

3. Group Memberships

If no explicit user entry exists, the system checks if the user belongs to the file's owning group or any other groups explicitly listed in the ACL. If matches are found, the user is granted the union of those group permissions (capped by the ACL Mask).

4. Other (World) Permissions / Default Deny

If the user does not match the owner, any explicit user entries, or any listed groups, the system applies the default "Other" permissions. If no rule explicitly grants the requested permission by the end of the evaluation, the system will automatically deny access (Default Deny).

What Does the ACL Mask Restrict?

1. Named Users

Any ACE explicitly assigning permissions to a specific user is capped by the mask.

2. Named Groups

Any ACE granting permissions to a group is capped by the mask.

3. The File Owner

The mask does not affect the base permissions assigned directly to the file owner.

Important Security Note: The ACL Mask never grants permissions, it only filters them. An effective permission can never exceed what the mask allows.

Procedure

Follow these steps to explore the ACL authorization engine:

1 Manage System Users

In the Simulation tab, use the System User Manager to create new operating system users and assign them to groups (e.g., devs, hr) independent of file permissions.

2 Select a Resource

Choose a target file (e.g., /finance/payroll.csv) from the dropdown. The current ACL for the file will load into the editor.

3 Modify the ACL & Mask

Use the ACL Editor to add a new Access Control Entry (ACE). Select a user, group, or ACL Mask, assign permissions, and click "Save Rule". Note how setting an ACL Mask caps the maximum allowed permissions for users and groups.

4 Initiate Access Request

In the Authorization Tester panel, select a Subject (the user attempting access) and an Operation (Read, Write, or Execute).

5 Run Simulation

Click the "Evaluate Access Request" button to trigger the authorization engine.

6 Analyze Trace

Read the step-by-step trace output to understand how the authorization engine evaluated the rules (including Root bypass and Mask filtering) to reach the final ALLOW or DENY decision.

7 Experiment (Precedence)

Give the "developers" group Write access, but explicitly give "Bob" (a developer) only Read access. Test Bob's write access to see how the explicit user rule overrides the group rule.

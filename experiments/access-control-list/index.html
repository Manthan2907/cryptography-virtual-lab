Access Control List (ACL)

Implement an Access Control List and demonstrate authorization based on assigned permissions.

Aim & Objectives

Aim: To study and implement an Access Control List (ACL) mechanism to determine whether a subject is permitted to perform a requested operation on an object, demonstrating fine-grained authorization.

Objectives:

  • Understand the Object-Centric Discretionary Access Control (DAC) paradigm.
  • Differentiate between standard UNIX permissions and extended POSIX Access Control Lists.
  • Configure Access Control Entries (ACEs) using read (r), write (w), and execute (x) privileges.
  • Simulate the authorization evaluation engine and precedence rules (Owner → Named User → Group → Other).
  • Analyze real-time access decisions mapped to POSIX ACL evaluation standards.

Theory

Introduction to Access Control

In computer security, access control is the process that restricts or grants subject (user or process) access to objects (files, directories, resources) based on administrative policies. Discretionary Access Control (DAC) leaves the granting of permissions to the discretion of the object's owner. Access Control Lists (ACLs) are the most common implementation of DAC.

Access Control Lists (ACL) vs Capability Lists

The Access Control Matrix (ACM) is a theoretical model representing rights: rows represent subjects, columns represent objects, and cells contain privileges. In practice, storing a sparse matrix is inefficient. Therefore, the matrix is decomposed in two ways:

  • Access Control List (Column-based): Attached to the object, listing which subjects have what rights. (e.g., File A → Alice: RW, Bob: R)
  • Capability List (Row-based): Attached to the subject, listing which objects they can access. (e.g., Alice → File A: RW, File B: R)

POSIX Access Control Lists

Standard UNIX file permissions support only three entities per file: the owner, the owning group, and others. Each has a combination of Read (r), Write (w), and Execute (x) privileges. However, this is too restrictive for complex sharing (e.g., granting read access to just one specific user outside the group). POSIX ACLs extend this model by allowing multiple users and multiple groups to have specific Access Control Entries (ACEs) on a single file.

ACL Evaluation Algorithm (Precedence Rules)

When a subject requests access (e.g., Read) to an object, the system checks the ACL using a strict precedence order. The first match determines the outcome, meaning specific rules override general ones:

  1. Owner Match: If the requesting user is the owner of the file, the owner permissions are applied. Evaluation stops.
  2. Named User Match: If there is a specific ACE for this user, those permissions are applied. Evaluation stops.
  3. Group Match: If the user is a member of the file's owning group, OR matches any named group ACEs, the union of matching group permissions is applied. Evaluation stops.
  4. Other: If none of the above match, the "other" (world) permissions are applied.

Finally, the granted permissions are checked against the requested operation. If the requested operation is within the granted permissions, access is ALLOWED; otherwise, it is DENIED.

Procedure

Follow these steps to explore the ACL authorization engine:

  1. Select a Resource: In the Simulation tab, choose a target file (e.g., /finance/payroll.csv or /var/www/index.html) from the dropdown. The current ACL for the file will load.
  2. Modify the ACL (Optional): Use the ACL Editor to add a new Access Control Entry (ACE). Select a user or group, assign permissions (Read, Write, Execute), and click "Add/Update Rule". Observe how the POSIX equivalent commands update.
  3. Initiate an Access Request: In the Authorization Tester panel, select a Subject (the user attempting access) and an Operation (Read, Write, or Execute).
  4. Run the Simulation: Click the "Evaluate Access" button.
  5. Analyze the Execution Trace: Read the step-by-step trace output to understand how the authorization engine evaluated the rules (matching user identity, traversing precedence logic) to reach the final ALLOW or DENY decision.
  6. Experiment with Precedence: Give the "developers" group Write access, but explicitly give "Bob" (a developer) only Read access. Test Bob's write access to see how the explicit user rule overrides the group rule.

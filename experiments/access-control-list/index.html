Access Control List (ACL)

Implement an Access Control List and demonstrate authorization based on assigned permissions.

Aim & Objectives

Aim: To study and simulate an Access Control List (ACL) mechanism, demonstrating how modern operating systems determine whether a subject is authorized to perform specific operations on a secured resource within a System Security framework.

Objectives:

  • Understand the foundational concept of Discretionary Access Control (DAC) as a core pillar of Operating System Security.
  • Analyze how core permission attributes (Read, Write, Execute) enforce Confidentiality and Integrity of sensitive data.
  • Examine the sequential rule-evaluation process that operating systems use to process access requests securely.
  • Configure Access Control Entries (ACEs) and observe real-time authorization decisions to prevent unauthorized privilege escalation.

Theory

Introduction to Access Control Lists in System Security

In the context of Cryptography and System Security, simply encrypting data is not always sufficient; the system must also tightly control who can access the cryptographic keys and protected resources. An Access Control List (ACL) is a fundamental security mechanism used by operating systems to manage these permissions. Conceptually, it is an authorized registry attached directly to a resource. This registry contains individual rules, known as Access Control Entries (ACEs), which specify exactly which users or groups are granted or denied access.

The Core Permissions for Confidentiality and Integrity

When a user is listed in an ACL, the system assigns them specific privileges defining what actions they can perform. In standard POSIX environments, these privileges map directly to core security principles:

  • Read (r) - Confidentiality: Grants the ability to open or view the file. Restricting this prevents unauthorized disclosure of sensitive data.
  • Write (w) - Integrity: Grants the ability to modify or delete the file's contents. Restricting this prevents unauthorized tampering or data corruption.
  • Execute (x) - System Safety: Grants the ability to run the file as a program. Restricting this prevents the execution of untrusted or malicious scripts.

The Sequential Evaluation Process

When a user attempts to access a protected file, the authorization engine does not evaluate the rules randomly. Instead, it processes the ACL in a strict, sequential order. The engine stops evaluating as soon as it finds a definitive match for the requesting user:

  1. Resource Owner: The system first checks if the user is the owner of the file. If true, the owner's specific permissions are applied, and evaluation stops.
  2. Explicit User Entries: If the user is not the owner, the system looks for an ACE that explicitly names the user. If found, those permissions are applied, and evaluation stops.
  3. Group Memberships: If no explicit user entry exists, the system checks if the user belongs to the file's owning group or any other groups explicitly listed in the ACL. If matches are found, the user is granted the union of those group permissions.
  4. Other (World) Permissions: If the user does not match the owner, any explicit user entries, or any listed groups, the system applies the default "Other" permissions, which apply to the general public.

The Principle of Default Deny

A critical component of secure ACL design is the Default Deny principle. If a user's request reaches the end of the evaluation process and no rule explicitly grants the requested permission, the system will automatically deny access. This ensures that resources remain secure by default.

Procedure

Follow these steps to explore the ACL authorization engine:

  1. Select a Resource: In the Simulation tab, choose a target file (e.g., /finance/payroll.csv or /var/www/index.html) from the dropdown. The current ACL for the file will load.
  2. Modify the ACL (Optional): Use the ACL Editor to add a new Access Control Entry (ACE). Select a user or group, assign permissions (Read, Write, Execute), and click "Add/Update Rule". Observe how the POSIX equivalent commands update.
  3. Initiate an Access Request: In the Authorization Tester panel, select a Subject (the user attempting access) and an Operation (Read, Write, or Execute).
  4. Run the Simulation: Click the "Evaluate Access" button.
  5. Analyze the Execution Trace: Read the step-by-step trace output to understand how the authorization engine evaluated the rules (matching user identity, traversing precedence logic) to reach the final ALLOW or DENY decision.
  6. Experiment with Precedence: Give the "developers" group Write access, but explicitly give "Bob" (a developer) only Read access. Test Bob's write access to see how the explicit user rule overrides the group rule.

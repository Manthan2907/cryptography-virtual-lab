Cryptographic Theory & Foundations

Explore the theoretical mechanisms behind adaptive key stretching, salt injection, and password storage security.

1. Hashing versus Encryption

A common misconception in system security is confusing hashing with encryption. Both use cryptographic mathematical primitives, but their mathematical properties and reversibility are completely opposite:

Cryptographic Hashing

Property: Strictly One-Way (Irreversible)

A cryptographic hash function H(m) = h deterministically transforms an arbitrary-length message $m$ into a fixed-length bit string $h$. There is no secret key that can invert $h$ back to $m$.

  • Primary Goal: Data integrity verification & non-recoverable authentication.
  • Input/Output: Arbitrary input → fixed output length (e.g. 60 chars in Bcrypt).
  • Typical Applications: Password databases, digital signatures, blockchain proof-of-work.

Encryption & Decryption

Property: Two-Way (Reversible via Key)

An encryption cipher Ek(m) = c scrambles plaintext $m$ into ciphertext $c$. Knowledge of the corresponding decryption key $k$ allows exact mathematical restoration of m = Dk(c).

  • Primary Goal: Confidentiality during data transmission or at-rest storage.
  • Input/Output: Ciphertext size is proportional to plaintext length.
  • Typical Applications: HTTPS/TLS tunnels, VPNs, BitLocker disk encryption, end-to-end messaging.
Key Takeaway: User passwords must never be encrypted. If an attacker breaches the database and discovers the decryption key, all passwords are immediately exposed. Passwords must always be hashed with slow, salted key derivation functions so that even if the entire database leaks, the original plaintext passwords cannot be reversed.

2. Why Bcrypt? The Vulnerability of Fast Hashing

Algorithms like MD5, SHA-1, and SHA-256 were created for high-throughput data integrity — verifying file checksums over gigabytes of data as quickly as possible. When applied to passwords, this efficiency is catastrophic.

100B+ / sec

SHA-256 computations/sec on modern GPU rigs

130K+ / sec

MD5 hashes/sec per basic cluster

~10 / sec

Bcrypt (Cost 10) intentionally throttled for defense

The GPU Brute-Force Threat: At 100 billion SHA-256 hashes per second, an attacker can exhaust all 8-character password combinations (letters, digits, and symbols = ≈ 6.7 × 1012 combinations) in under 70 seconds. The same attack against Bcrypt at cost 10 requires over 21 years of continuous GPU execution.

Provos and Mazières Design (1999)

Presented at the USENIX Annual Technical Conference by Niels Provos and David Mazières at OpenBSD, Bcrypt introduces two defenses:

  • Key Stretching: Thousands of iterative Blowfish cipher key expansions intentionally consume CPU clock cycles and memory registers.
  • Configurable Work Factor: An adaptive cost parameter allowing administrators to scale computation work higher over time as computing hardware becomes more powerful.

3. Cryptographic Salt & Exponential Work Factor Scaling

A Cryptographic Salt is a unique 128-bit (16-byte) random value generated by a cryptographically secure pseudorandom number generator (CSPRNG) for each password. Bcrypt automatically embeds this salt into the final output string.

1. Defeats Rainbow Tables

Precomputed hash lookup tables (rainbow tables) map millions of plaintext passwords to their precalculated hashes. Because each user has a unique 128-bit salt, an attacker must compute a custom rainbow table of 2128 entries specifically for that single user, rendering precomputation economically impossible.

2. Prevents Hash Correlation

Without a salt, two users choosing the same password (e.g. Secret123) produce identical hashes in the database. With unique salts, identical passwords produce completely different, uncorrelated hash strings.

The Exponential Work Formula

Bcrypt's Blowfish key expansion loop scale exponentially with the cost parameter C:

5. The 72-Byte Password Limitation in Eksblowfish

Bcrypt is based on Eksblowfish (Expensive Key Schedule Blowfish). The Blowfish cipher was designed in 1993 with a maximum key schedule buffer of 448 bits = 56 to 72 bytes. In Bcrypt, any input password exceeding 72 bytes is silently truncated.

Silent Truncation Vulnerability

Password 1: "A" × 72 bytes + "SecretTail1"

Password 2: "A" × 72 bytes + "DifferentTail2"

= Both produce the EXACT SAME Bcrypt hash digest!

Industry Workaround: SHA-256 Pre-Hashing

Modern web frameworks (e.g. Django, Laravel, Ruby on Rails) handle this limitation by pre-hashing passwords using SHA-256 before passing them to Bcrypt:

User Password (Arbitrary Length) → SHA-256 Digest (32 raw bytes) → Base64 Encode (44 ASCII chars) → Bcrypt Input (44 < 72 bytes ✅)

Because SHA-256 is collision-resistant and always produces exactly 32 bytes, the 44-character Base64 string fits safely within the 72-byte ceiling while preserving the uniqueness of any password length.

6. Eksblowfish Architecture: Subkeys, P-Arrays & 4KB L1 Cache Footprint

Standard Blowfish uses a fast key schedule, which would make it weak against brute force. Provos and Mazières replaced it with Eksblowfish (Expensive Key Schedule Blowfish), turning key setup into an intentionally heavy computational bottleneck.

Internal State Components

  • P-Array: 18 32-bit subkeys (P1, P2, …, P18 = 72 bytes).
  • Four S-Boxes (S1, S2, S3, S4): Each S-box holds 256 32-bit words (4 × 256 × 4 bytes = 4,096 bytes = 4 KB).
  • Total Working State: Exactly 4,168 bytes.

This state is initialized with digits from the fractional part of π, ensuring "nothing-up-my-sleeve" cryptographic constants.

Why the 4KB Cache Size Deters GPUs

In standard algorithms (like MD5 or SHA-256), the internal state is only 64 bytes, fitting entirely inside small registers. A modern GPU can run thousands of parallel threads simultaneously.

In Bcrypt, each thread requires its own 4KB working set in high-speed L1 cache. Because GPU Streaming Multiprocessors (SMs) share limited L1/shared memory, the GPU quickly runs out of cache and experiences catastrophic memory thrashing, severely limiting parallel cracking throughput!

The Eksblowfish Key Expansion Loop

During key stretching, the algorithm alternates between encrypting subkeys with the salt and with the password:

state = InitStateWithPiDigits()
state = ExpandKey(state, salt, password)
repeat 2Cost times:
  state = ExpandKey(state, 0, password)
  state = ExpandKey(state, 0, salt)
return state
Pro Tip: Notice that both the password AND the salt are fed into the state repeatedly in every one of the 2C iterations. An attacker cannot precompute any intermediate state without knowing both!

7. Evolution of Bcrypt Revisions: $2, $2a, $2x, $2y, and $2b

Over the past 25 years, subtle implementation discrepancies and software bugs led to multiple revision prefixes in the modular format:

Prefix Year & Origin Characteristics & Historical Context Security Status
$2$ 1999 (OpenBSD) Original specification by Provos & Mazières. Rarely seen today. Deprecated
$2a$ Early 2000s Added UTF-8 string handling. Discrepancies arose in how libraries handled characters with high bits. Legacy
$2x$ 2011 (PHP 5.3) Buggy crypt_blowfish implementation: characters with 8th bit set caused sign extension, reducing effective password entropy to 7 bits. Vulnerable
$2y$ 2011 (PHP 5.3.7) Introduced specifically by PHP developers to mark hashes generated with the sign-extension bug fixed. Acceptable
$2b$ 2014 (OpenBSD) Fixed a password buffer length wraparound bug where length % 256 allowed 255-byte overflows. The current gold standard across all modern languages. ✓ Current Standard

8. Modern Password Security: Bcrypt vs. Argon2id, Pepper & Migration

While Bcrypt remains widely used and battle-tested for over two decades, modern authentication security incorporates defense-in-depth measures:

Salt vs. Pepper Architecture

  • Salt (Random & Public): Generated per-user, stored directly in plaintext beside the hash in the database. Primary role: defeats rainbow tables and correlation.
  • Pepper (Secret & Centralized): A secret cryptographic HMAC key stored outside the database (e.g. in AWS KMS, Azure Key Vault, or an HSM). Primary role: if the database leaks via SQL injection, the attacker cannot crack the hashes without the Pepper key!

Dynamic Re-Hashing on Login

How do websites upgrade security when changing cost factor from 10 to 12, or migrating from MD5 to Bcrypt?

Whenever a user logs in, the server verifies the plaintext password against the old hash. If verification succeeds and the server detects the hash uses an outdated cost factor, it transparently computes a fresh hash with the new cost factor and updates the database row.

📚 Cryptographic Concept Glossary

Cryptographic Salt

A unique random bit string (128 bits in Bcrypt) combined with a password before hashing. Defeats precomputed rainbow table dictionaries and prevents identical passwords from producing identical hashes.

Pepper (Secret Key)

A secret cryptographic key shared across the application and stored outside the database (in an HSM or KMS). Adds defense-in-depth against SQL injection breaches.

Cost Factor ($C$) & Key Stretching

An exponential parameter where internal loop rounds equal 2C. Key stretching deliberately consumes CPU clock cycles to make brute force computationally unfeasible.

CSPRNG

Cryptographically Secure Pseudorandom Number Generator. Uses unpredictable system entropy sources (e.g. crypto.getRandomValues) rather than mathematical formulas like Math.random().

Constant-Time Comparison

A string comparison algorithm (e.g. timingSafeEqual) that always inspects all bytes regardless of where differences occur, preventing side-channel timing attacks.

Radix-64 Encoding

A customized 64-character alphabet used by Bcrypt (./ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789) differing slightly from standard MIME Base64.

⚙️ Eksblowfish Feistel Network & 4KB L1 Cache Footprint

16-Round Feistel Cipher Architecture

Eksblowfish is derived from Bruce Schneier's Blowfish cipher, which operates on 64-bit plaintext blocks split into two 32-bit halves (L, R):

For i = 1 to 16 rounds:
  L = L ⊕ P[i]
  R = F(L) ⊕ R
  Swap(L, R)
Swap(L, R) [Undo final swap]
R = R ⊕ P[17]
L = L ⊕ P[18]
Output: (L, R) 64-bit ciphertext

The Feistel Function F(x)

Splits a 32-bit word into 4 8-bit bytes (a, b, c, d) and accesses four substitution boxes:

F(a, b, c, d) = ((S1[a] + S2[b]) ⊕ S3[c]) + S4[d]   (mod 232)

Why the 4,096-Byte Working State Deters GPU Cracking

Each of the four S-boxes has 256 entries of 4 bytes (4 × 256 × 4 bytes = 4,096 bytes = 4 KB). Modern GPUs contain thousands of lightweight compute cores designed to run threads sharing small register files.

GPU Bottleneck: Because every Bcrypt thread needs 4KB of state in low-latency L1 cache, GPU Streaming Multiprocessors (SMs) rapidly exhaust high-speed cache lines. Threads stall waiting on high-latency GDDR memory, slashing GPU cracking efficiency from billions of hashes/second (like SHA-256) down to thousands per second.

🎲 Salt Entropy & Rainbow Table Neutralization

Mathematical Proof: Why Rainbow Tables Fail

A rainbow table is a precomputed lookup table trading storage for time. It maps plaintext passwords to precalculated hashes. For an unsalted hash:

Plaintext "password" → Hash 5f4dcc3b5aa765d61d8327deb882cf99 (MD5)
Attacker checks lookup table → Matches in < 0.001 ms!

With a 128-Bit CSPRNG Salt:

Bcrypt generates 16 bytes = 128 bits of entropy per password:

Total Possible Salts = 2128 ≈ 3.402 × 1038 combinations

Even if an attacker stored 1 billion rainbow tables per second on petabytes of hard drives, generating tables for all possible 128-bit salts would take longer than the age of the universe.

CSPRNG vs. Pseudo-Random Number Generators

Never use Math.random(): In JavaScript, Math.random() uses the XorShift128+ algorithm, which is completely predictable. Always use window.crypto.getRandomValues() to query the operating system kernel's true hardware entropy pool!

📜 Bcrypt Revisions History: $2, $2a, $2x, $2y, $2b

Why do Bcrypt hashes start with $2b$ rather than $2$ or $2a$? Here is the complete historical roadmap:

$2$ (1999) — Original Specification

Published by Niels Provos & David Mazières at OpenBSD. Did not specify character encoding handling.

$2a$ (Early 2000s) — UTF-8 Encoding Revision

Introduced to standardize UTF-8 strings. However, different C compilers on x86 architectures treated char as signed vs unsigned, causing incompatible hashes for non-ASCII characters.

$2x$ (2011) — The Sign Extension Bug

In PHP 5.3's crypt_blowfish implementation, characters with the 8th bit set underwent sign extension to 32 bits, corrupting the key schedule and discarding 1 bit of entropy per character.

$2y$ (2011) — PHP Fix Prefix

PHP developers introduced $2y$ to distinguish hashes generated after the sign extension bug was corrected from vulnerable $2x$ hashes.

$2b$ (June 2014) — OpenBSD Buffer Fix & Current Standard

Fixed a subtle buffer overflow where password lengths congruent to 0 mod 256 could wrap around the key length counter in OpenBSD. $2b$ is the universal production baseline today.

🛡️ Pepper vs. Salt & Dynamic Re-Hashing Architecture

Defense-in-Depth: Salt vs Pepper

Cryptographic Salt
  • Random per user
  • Stored directly in the database row
  • Publicly visible in the hash string
  • Role: Prevents rainbow tables and correlation
Secret Pepper Key
  • Single secret key for the application
  • Stored in KMS / HSM outside the database
  • Never stored in the database
  • Role: Neutralizes stolen SQL database dumps

How Dynamic Re-Hashing Works on Login

Suppose you want to upgrade your database from Cost 10 to Cost 12:

1. User submits login form with plaintext password.
2. Server queries DB, fetches stored hash with Cost 10.
3. Server verifies password against stored hash → MATCH!
4. Server checks: `needsRehash(storedHash, newCost: 12)` → TRUE!
5. Server hashes plaintext password with Cost 12.
6. Server updates DB record with fresh Cost 12 hash.
7. User logs in seamlessly without resetting their password!

🔍 Step-by-Step Bcrypt Verification Internals

Students often ask: "If hashing is strictly one-way and cannot be decrypted, how does Bcrypt check if a password is correct?"

1
Extract Parameters from Stored Hash

The verifier parses the 60-character target hash: it extracts the cost factor (C) and the 22-character (16-byte) CSPRNG salt.

2
Re-Compute Eksblowfish Hash

The verifier feeds the candidate password submitted by the user together with the extracted salt into the Eksblowfish key schedule for 2C rounds, encrypting the constant text.

3
Constant-Time String Comparison

The newly generated hash is compared to the stored hash using a constant-time comparison function (timingSafeEqual). If all bytes match, authentication is granted!

Constant-Time Immunity: By taking the exact same amount of time regardless of whether the first byte or the last byte differed, Bcrypt prevents hackers from using microscopic latency variations to guess passwords byte-by-byte (side-channel timing attack).

✂️ Technical Root Cause of 72-Byte Key Truncation

Why 72 Bytes?

Bruce Schneier designed Blowfish in 1993 with variable key lengths up to 448 bits. The P-array contains 18 32-bit subkeys ($18 \times 32 = 576\text{ bits} = 72\text{ bytes}$).

for (i = 0; i < 18; ++i) {
  P[i] = P[i] ⊕ key_bytes[(i * 4) % key_len];
}

In standard Eksblowfish, the key schedule loop copies at most 72 UTF-8 bytes into internal key buffers. Any byte at index 72 or higher is simply never referenced in the C loop!

The Pre-Hashing Defense Pattern

Industry Standard: Pre-hash the user password with SHA-256 before feeding it to Bcrypt. SHA-256 takes passwords of arbitrary length and produces a 32-byte binary digest. Encoded as Base64 (44 ASCII characters), this is guaranteed to fit within the 72-byte limit while preserving complete cryptographic uniqueness.

💡 How Bcrypt Latency & Work Factor are Calculated

The Latency Formula

Bcrypt's execution time $T$ is governed by the CPU work formula:

T ≈ 2Cost Factor × Tsingle round

Each increment in Cost Factor $C$ exactly doubles the computational rounds:

  • Cost 4: 24 = 16 rounds (≈ 1 ms)
  • Cost 8: 28 = 256 rounds (≈ 15-25 ms)
  • Cost 10: 210 = 1,024 rounds (≈ 100-150 ms)
  • Cost 12: 212 = 4,096 rounds (≈ 400-600 ms)
OWASP Recommendation: OWASP recommends calibrating C so that a single login check takes between 250 ms and 500 ms on the target server. This is unnoticeable to a human user logging in once, but devastating to an automated bot guessing passwords!

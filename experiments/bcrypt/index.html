Bcrypt Password Hashing & Security Analysis

Implement bcrypt adaptive password hashing and verification, evaluate salt randomness and non-determinism, analyze exponential cost factor scaling, inspect modular hash string formatting, and investigate the 72-byte key truncation limit.

Aim & Objectives

Aim: To study, implement, and analyze the Bcrypt adaptive password hashing algorithm. This includes understanding the role of cryptographic salts in defeating rainbow table attacks, evaluating the exponential work factor formula (2Cost Factor), parsing modular hash string components, verifying passwords client-side, and analyzing the 72-byte key truncation limitation inherent to Eksblowfish.

Learning Objectives

Upon completing this laboratory module, students will be able to:

  • Differentiate Hashing from Encryption: Articulate the theoretical and practical differences between irreversible one-way hash digests and reversible two-way ciphertexts.
  • Evaluate Fast vs. Slow Hashing Vulnerabilities: Explain why high-throughput algorithms (MD5, SHA-1, SHA-256) are dangerous for password storage due to GPU-accelerated brute-force attacks computing billions of hashes per second.
  • Analyze Salt Entropy & Non-Determinism: Demonstrate how unique 128-bit random salts prevent duplicate password correlation in breached databases and neutralize precomputed lookup (rainbow) tables.
  • Formulate the Work Factor Scaling: Calculate the exponential relationship between the cost factor parameter $C$ and the internal key expansion rounds ($2^C$).
  • Dissect Modular Hash Formatting: Parse and decode standard 60-character Bcrypt output strings into algorithm prefix, cost factor, Radix-64 encoded salt, and ciphertext digest.
  • Investigate Eksblowfish Key Limits: Identify the 72-byte password length boundary and implement the industry-standard SHA-256 pre-hashing mitigation pattern.

Cryptographic Theory & Foundations

Explore the theoretical mechanisms behind adaptive key stretching, salt injection, and password storage security.

1. Hashing versus Encryption

A common misconception in system security is confusing hashing with encryption. Both use cryptographic mathematical primitives, but their mathematical properties and reversibility are completely opposite:

Cryptographic Hashing

Property: Strictly One-Way (Irreversible)

A cryptographic hash function $H(m) = h$ deterministically transforms an arbitrary-length message $m$ into a fixed-length bit string $h$. There is no secret key that can invert $h$ back to $m$.

  • Primary Goal: Data integrity verification & non-recoverable authentication.
  • Input/Output: Arbitrary input → fixed output length (e.g. 60 chars in Bcrypt).
  • Typical Applications: Password databases, digital signatures, blockchain proof-of-work.

Encryption & Decryption

Property: Two-Way (Reversible via Key)

An encryption cipher $E_k(m) = c$ scrambles plaintext $m$ into ciphertext $c$. Knowledge of the corresponding decryption key $k$ allows exact mathematical restoration of $m = D_k(c)$.

  • Primary Goal: Confidentiality during data transmission or at-rest storage.
  • Input/Output: Ciphertext size is proportional to plaintext length.
  • Typical Applications: HTTPS/TLS tunnels, VPNs, BitLocker disk encryption, end-to-end messaging.
Key Takeaway: User passwords must never be encrypted. If an attacker breaches the database and discovers the decryption key, all passwords are immediately exposed. Passwords must always be hashed with slow, salted key derivation functions so that even if the entire database leaks, the original plaintext passwords cannot be reversed.

2. Why Bcrypt? The Vulnerability of Fast Hashing

Algorithms like MD5, SHA-1, and SHA-256 were created for high-throughput data integrity — verifying file checksums over gigabytes of data as quickly as possible. When applied to passwords, this efficiency is catastrophic.

100B+ / sec

SHA-256 computations/sec on modern GPU rigs

130K+ / sec

MD5 hashes/sec per basic cluster

~10 / sec

Bcrypt (Cost 10) intentionally throttled for defense

The GPU Brute-Force Threat: At 100 billion SHA-256 hashes per second, an attacker can exhaust all 8-character password combinations (letters, digits, and symbols = $\approx 6.7 \times 10^{12}$ combinations) in under 70 seconds. The same attack against Bcrypt at cost 10 requires over 21 years of continuous GPU execution.

Provos and Mazières Design (1999)

Presented at the USENIX Annual Technical Conference by Niels Provos and David Mazières at OpenBSD, Bcrypt introduces two defenses:

  • Key Stretching: Thousands of iterative Blowfish cipher key expansions intentionally consume CPU clock cycles and memory registers.
  • Configurable Work Factor: An adaptive cost parameter allowing administrators to scale computation work higher over time as computing hardware becomes more powerful.

3. Cryptographic Salt & Exponential Work Factor Scaling

A Cryptographic Salt is a unique 128-bit (16-byte) random value generated by a cryptographically secure pseudorandom number generator (CSPRNG) for each password. Bcrypt automatically embeds this salt into the final output string.

1. Defeats Rainbow Tables

Precomputed hash lookup tables (rainbow tables) map millions of plaintext passwords to their precalculated hashes. Because each user has a unique 128-bit salt, an attacker must compute a custom rainbow table of $2^{128}$ entries specifically for that single user, rendering precomputation economically impossible.

2. Prevents Hash Correlation

Without a salt, two users choosing the same password (e.g. Secret123) produce identical hashes in the database. With unique salts, identical passwords produce completely different, uncorrelated hash strings.

The Exponential Work Formula

Bcrypt's Blowfish key expansion loop scale exponentially with the cost parameter $C$:

$$\text{Iterations} = 2^{\text{Cost Factor}}$$
Cost Factor ($C$) Formula Iterations Typical Latency Recommended Application
4 $2^4$ 16 ~1 ms Unit testing only
8 $2^8$ 256 ~15 ms Resource-constrained legacy microcontrollers
10 $2^{10}$ 1,024 ~100 ms ✓ Recommended Production Baseline
12 $2^{12}$ 4,096 ~400 ms High-security applications & administrative logins
14 $2^{14}$ 16,384 ~1.6 s Government & financial transaction vaults

4. Dissecting the 60-Character Bcrypt Hash String

Bcrypt packages all information required for password authentication into a single 60-character ASCII string using Radix-64 encoding:

$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
$2b$

Algorithm Version

OpenBSD revision B (2014), which fixed a signed char wraparound security bug present in older $2a$ implementations.

10$

Cost Factor

Two decimal digits indicating work factor $C=10$ ($2^{10} = 1,024$ rounds of key schedule loop).

22 Characters

128-bit Salt

16 raw bytes of CSPRNG random salt mapped to 22 Radix-64 characters.

31 Characters

192-bit Digest

24 raw bytes resulting from 64 rounds of Blowfish encryption of constant text, Radix-64 encoded.

5. The 72-Byte Password Limitation in Eksblowfish

Bcrypt is based on Eksblowfish (Expensive Key Schedule Blowfish). The Blowfish cipher was designed in 1993 with a maximum key schedule buffer of 448 bits = 56 to 72 bytes. In Bcrypt, any input password exceeding 72 bytes is silently truncated.

Silent Truncation Vulnerability

Password 1: "A" × 72 bytes + "SecretTail1"

Password 2: "A" × 72 bytes + "DifferentTail2"

= Both produce the EXACT SAME Bcrypt hash digest!

Industry Workaround: SHA-256 Pre-Hashing

Modern web frameworks (e.g. Django, Laravel, Ruby on Rails) handle this limitation by pre-hashing passwords using SHA-256 before passing them to Bcrypt:

User Password (Arbitrary Length) → SHA-256 Digest (32 raw bytes) → Base64 Encode (44 ASCII chars) → Bcrypt Input (44 < 72 bytes ✅)

Because SHA-256 is collision-resistant and always produces exactly 32 bytes, the 44-character Base64 string fits safely within the 72-byte ceiling while preserving the uniqueness of any password length.

Stage 1: Input Pre-processing & 72-Byte Validation

The plaintext password is converted to a UTF-8 byte stream. If the password exceeds 72 bytes, bytes past position 71 are silently discarded due to Blowfish key schedule constraints.

Sample: "Crypt@2026Lab" (13 Bytes) → Accepted without truncation

Stage 2: 128-bit CSPRNG Salt Generation

A Cryptographically Secure Pseudorandom Number Generator generates 16 raw random bytes (128 bits). This salt guarantees uniqueness and immunizes the hash against rainbow table precomputation.

Raw Salt (16 Bytes): 0xA4 0x7E 0x90 0x12 0x55 0xBC 0x7F 0x3A 0x9B 0x11 0x4E 0xC8 0xD2 0x0F 0x88 0x31

Stage 3: Eksblowfish Key Expansion ($2^{\text{Cost}}$ Loops)

Password and salt are iteratively fed into the Expensive Key Schedule (Eksblowfish). The loop runs $2^C$ times (e.g. 1,024 rounds at Cost 10), repeatedly interweaving salt and password bytes into the P-array and S-boxes.

Iterating 1,024 rounds of state perturbation... [CPU & Memory Hard]

Stage 4: 64 Rounds of Blowfish Encryption

Using the expanded key state, the constant 192-bit string "OrpheanBeholderScryDoubt" is encrypted 64 times in ECB mode to produce the 24-byte (192-bit) digest.

Target: "OrpheanBeholderScryDoubt" → Encrypted to 24 raw bytes

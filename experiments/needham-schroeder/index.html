Needham-Schroeder Symmetric Key Protocol

Simulate the 5-message symmetric-key authentication protocol and demonstrate the establishment of a shared session key between two entities.

Aim

To simulate the Needham-Schroeder symmetric-key authentication protocol and demonstrate the establishment of a shared session key between two communicating entities mediated by a Key Distribution Center (KDC).

Objectives

  • Explain the need for a trusted third party (KDC) in symmetric key distribution.
  • Trace the 5 message exchanges in the Needham-Schroeder protocol.
  • Simulate the generation and verification of nonces for freshness.
  • Identify the vulnerability of the protocol to replay attacks (Denning-Sacco).
  • Compare the original protocol with the timestamp-based fix used in systems like Kerberos.

Prerequisites

Basic understanding of symmetric encryption (e.g., AES) and the concept of a shared secret key.

What you will observe

You will see how Alice and Bob exchange messages via the KDC to establish a secure session key. You will observe how encryption protects the ticket, how nonces ensure freshness, and how a compromised old key can be used by an attacker to launch a replay attack.

Need for Authentication & Key Distribution

In a network with N users, symmetric cryptography requires N(N-1)/2 keys if every pair shares a key. This is unscalable. A Key Distribution Center (KDC) solves this by sharing a long-term key with each user. When Alice wants to talk to Bob, the KDC generates a temporary session key and distributes it securely to both.

Protocol Concepts

  • Nonces: A nonce (number used once) is a random value generated for a specific protocol run. It ensures freshness—if a nonce sent in message 1 is returned inside an encrypted message 2, the sender knows message 2 was freshly generated, preventing replay of old messages.
  • The Ticket: A block of data meant for Bob, encrypted with Bob's long-term key. Alice cannot read it, but she forwards it to Bob.

The 5 Messages

  1. A → S : A, B, Na
    Alice tells the KDC she wants to talk to Bob and sends her nonce Na.
  2. S → A : {Na, B, Kab, {Kab, A}Kbs}Kas
    The KDC replies with a message encrypted with Alice's key Kas. Inside, Alice finds her nonce (proving freshness), Bob's identity (proving it's for Bob), the new session key Kab, and the ticket {Kab, A}Kbs.
  3. A → B : {Kab, A}Kbs
    Alice forwards the ticket to Bob. Bob decrypts it with his key Kbs and learns Kab and that Alice is the initiator.
  4. B → A : {Nb}Kab
    Bob generates his own nonce Nb, encrypts it with the new session key, and sends it to Alice as a challenge.
  5. A → B : {Nb - 1}Kab
    Alice decrypts, subtracts 1 from Nb (to prove she can manipulate the data), encrypts it with Kab, and sends it back to authenticate herself to Bob.

Security Goals Achieved

The protocol achieves mutual authentication, key confidentiality, and key freshness for Alice.

Vulnerability: The Denning-Sacco Replay Attack

In 1981, Denning and Sacco pointed out a flaw: Bob has no way to check that message 3 is fresh. If an attacker (Mallory) compromises an old session key Kab, she can replay an old ticket {Kab, A}Kbs to Bob. Bob will accept it, and Mallory can impersonate Alice.

The Fix: Add timestamps or lifetimes to the ticket. This ensures Bob rejects stale tickets. This concept is foundational to Kerberos.

Key Points

  • KDC distributes session keys using long-term keys.
  • Nonces prove freshness for Alice, but not for Bob in the original protocol.
  • Replay attacks exploit the lack of freshness guarantees for Bob's ticket.

Procedure

  1. Go to the Simulation tab.
  2. Setup: Enter identifiers for Alice and Bob, or leave the defaults. Observe the pre-shared keys (Kas, Kbs) derived from passphrases.
  3. Scenario Selection: Choose a scenario from the dropdown (e.g., Normal Run, Replay Attack).
  4. Step-by-Step Execution: Click "Next Step" to trace the protocol message by message.
    • Observe how knowledge panels update as entities learn nonces and keys.
    • Click on ciphertext in the Message Log to see its decrypted form.
  5. Attack Scenarios:
    • Run the "Replay attack by Mallory" scenario. Note how Bob accepts the compromised key.
    • Run the "Replay attack with Timestamp fix ON" scenario. Observe how Bob rejects the stale ticket.
  6. Results: Check the Observations & Results panel to see if mutual authentication was achieved.
Real lab vs virtual lab note: In a real implementation, keys are typically 256-bit random bytes rather than derived from short passphrases, and messages are sent over TCP/UDP sockets rather than simulated in a single browser window. We use AES-256-GCM for encryption as a modern standard, though the original 1978 paper assumed DES.

Needham-Schroeder Symmetric Key Protocol

Simulate the 5-message symmetric-key authentication protocol and demonstrate the establishment of a shared session key between two entities.

Estimated Time

1 hour

Learning Objective of the Experiment

To identify, trace, and analyze the steps of the Needham-Schroeder Symmetric Key Protocol (1978) for establishing a temporary shared secret key and achieving mutual authentication between two untrusted network nodes via a trusted Server (Key Distribution Center / KDC).

  • Understand the architectural role of a centralized Server (KDC) in symmetric key management.
  • Analyze how Alice's Random Challenge Number (N_A) and Bob's Random Challenge Number (N_B) prevent replay attacks.
  • Observe ticket generation and ticket forwarding mechanics.
  • Evaluate challenge-response nonce verification (N_B - 1) for mutual authentication.

Theory & Beginner Guide

1. Why we need it

Two parties on an insecure network who have never met need (i) to prove who they are to each other (authentication) and (ii) a fresh secret key to protect their conversation (key distribution). With symmetric cryptography each pair of users would need its own pre-shared key. Needham and Schroeder (1978) [1] proposed using a trusted authentication server so that each user only shares ONE long-term key, with the server.

Scalability point: n users need n long-term keys (one per user, held by the server) instead of n(n-1)/2 pairwise keys. Example: 100 users → 100 keys vs 4,950 keys.

3. Assumptions and threat model
  • The network is insecure: an attacker can read, insert, delete and modify messages. [1][4]
  • Each user's own machine is secure (encryption works as expected, keys do not leak).
  • S is trusted and holds every long-term key; Kas and Kbs were shared with S out of band before the protocol starts.
  • Encryption is assumed to guarantee that a message cannot be altered or forged without the key. In the simulator AES-256-GCM provides this explicitly through its authentication tag; a wrong key or tampering therefore shows as "decryption failed".
  • The original paper used DES; AES-256-GCM [8][9][10] is the modern stand-in here.
Warning: The original protocol relied solely on encryption for integrity, which can be vulnerable without proper modes like GCM.

4. Key ideas

Nonce: a random number used once. If a reply contains my fresh nonce, the reply must have been created after my request, so it cannot be an old recording. Nonces give FRESHNESS, not secrecy.

Ticket: S encrypts Kab for B under Kbs and gives it to A. A cannot read or alter it, but forwards it, so S never has to talk to B directly.

Session key: Kab is generated by S, used for one session, then discarded.

Handshake (messages 4-5): B sends {Nb}Kab and A must return {Nb - 1}Kab. This proves A really holds Kab. Returning Nb - 1 (not Nb) stops an attacker from simply reflecting B's own message 4 back.

5. The protocol, message by message
  1. A -> S : A, B, Na
    A asks S for a key to talk to B and includes a fresh nonce. Sent in clear.
  2. S -> A : {Na, B, Kab, {Kab, A}Kbs}Kas
    S generates Kab. Only A can decrypt this (Kas). A checks: Na matches (reply is fresh, not a replay of an old message 2) and B is the intended peer (the request was not altered in transit). A now knows Kab and holds the ticket.
  3. A -> B : {Kab, A}Kbs
    A forwards the ticket. B decrypts with Kbs and learns Kab and that it is meant for a conversation with A.
  4. B -> A : {Nb}Kab
    B challenges A with a fresh nonce under the new key.
  5. A -> B : {Nb - 1}Kab
    A proves possession of Kab. B checks Nb - 1 and accepts.

Result: A and B share Kab, and each has some evidence about the other. [1][6]

7. Security goals achieved
  • Session key confidentiality: Kab only ever travels encrypted under Kas or Kbs.
  • Key freshness FOR A: guaranteed by Na.
  • Mutual authentication: A is convinced the key came from S for talking to B; B is convinced A holds Kab (messages 4-5).
  • Weakness: B has NO freshness guarantee for the ticket in message 3 (see next section).

Try it in the simulation: (a) normal run

8. The weakness: Denning-Sacco replay attack (1981)

Assumption: Mallory recorded the old ticket {Kab, A}Kbs from a previous session and has since obtained that old Kab (stolen, or cracked because old keys are weaker). [2][6][7]

Attack: Mallory replays the old ticket to B (message 3). B decrypts it with Kbs and cannot tell it is old. B sends {Nb'}Kab. Mallory decrypts with the old Kab and replies {Nb' - 1}Kab. B now believes it is talking to A and shares Kab with A. Mallory never needed Kas, Kbs or any live help from S.

Cause: nonce Na protects only A; nothing protects B against an old ticket.

9. The fix: timestamps

S adds a timestamp T to message 2 and to the ticket: [2][7]

  1. A -> S : A, B
  2. S -> A : {B, Kab, T, {Kab, A, T}Kbs}Kas
  3. A -> B : {Kab, A, T}Kbs

B accepts only if |Clock_B - T| < Dt1 + Dt2, where Dt1 is the allowed difference between S's clock and B's clock and Dt2 is the expected network delay. An old ticket therefore fails the check. Trade-offs: clocks must be synchronised and the time source must be trustworthy.

Denning and Sacco also note that timestamps can replace the two-step handshake. Another remedy is to make B contribute a fresh nonce that S binds into the ticket (the "amended" protocol; see [6] for its specification).

Key point: Do not confuse this symmetric-key protocol with the Needham-Schroeder PUBLIC-key protocol, which has a different flaw (man-in-the-middle, found by Lowe in 1995).

11. Limitations to mention

Single point of failure and trust (S knows every key and every session key); no ticket lifetime in the basic protocol; if long-term keys are derived from passwords they can be guessed offline; 1978 DES keys (56-bit) are far too weak today.

13. Key points summary
  • Purpose: Mutual authentication and secure distribution of a shared session key via a trusted KDC.
  • The 5 Messages: 1 request, 1 KDC response, 1 ticket forwarding, 2 handshake steps.
  • Role of Na: Ensures the KDC's response (and the session key) is fresh for Alice.
  • Role of the ticket: Securely delivers the session key to Bob, proving S generated it.
  • Role of Nb-1: Proves to Bob that Alice successfully decrypted the handshake challenge.
  • Replay Weakness & Fix: Bob cannot verify ticket freshness (Denning-Sacco attack); fixed using timestamps.

Try it in the simulation: (a) normal run

14. Check yourself
1. Why does message 2 contain Na? Proves reply is fresh for A.
2. Why is B's name inside message 2? A can detect a changed request.
3. Who can read the ticket? Only B and S; A cannot.
4. Why Nb - 1 and not Nb? Prevents reflecting message 4 back.
5. What must the attacker possess for the Denning-Sacco attack? An old ticket and its old Kab.
6. How do timestamps stop the attack? B rejects a ticket whose T is outside the allowed window.

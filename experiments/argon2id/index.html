Argon2id Password Hashing

Implement Argon2id for password hashing and compare its output and computational parameters with conventional hash functions.

Theory

Aim

To implement Argon2id password hashing and verification, and to compare its output and computational parameters with conventional hash functions (MD5, SHA-1, SHA-256 and PBKDF2-SHA256).

Objectives

After this experiment you should be able to: (1) hash a password with Argon2id and read the encoded result; (2) explain how memory cost, time cost and parallelism change the work done; (3) verify a password against a stored hash; (4) explain why fast general-purpose hashes are unsuitable for storing passwords.

Hashing versus encryption

Encryption is reversible with a key. A hash function is one-way: it maps any input to a fixed-length digest and there is no key to undo it. Systems therefore store a hash of the password, never the password itself. At login the entered password is hashed again and the two results are compared.

Why SHA-256 or MD5 alone is not enough

MD5, SHA-1 and SHA-256 are designed to be fast. A fast hash lets an attacker who steals a database test billions of guesses per second on GPUs. Passwords also come from a small, predictable set of choices, so speed helps the attacker directly. Password hashing needs a deliberately expensive function.

Salt

A salt is a random value stored next to the hash and mixed into it. The same password with two different salts gives two different hashes, so identical passwords cannot be spotted and precomputed (rainbow) tables become useless. A salt is not secret; its job is uniqueness. Argon2 requires at least 8 bytes, and 16 random bytes is recommended.

Argon2 and its variants

Argon2 won the Password Hashing Competition in 2015 and is specified in RFC 9106. It is memory-hard: it fills a large block of memory and repeatedly reads it in an order that is hard to shortcut, so cheap parallel hardware loses its advantage. Argon2d uses data-dependent memory access (strong against GPU cracking but exposed to side-channel timing attacks). Argon2i uses data-independent access (resistant to side channels but weaker against time-memory trade-offs). Argon2id combines them: the first half of the first pass is data-independent and the rest is data-dependent. RFC 9106 and OWASP recommend Argon2id for password hashing.

Parameters

Memory cost (m) is the memory used, in KiB. Time cost (t) is the number of passes over that memory. Parallelism (p) is the number of independent lanes. Raising m or t makes each guess more expensive for the defender and the attacker alike, so you choose values that keep login acceptably fast on your server. The output length here is 32 bytes.

Encoded output and verification

Argon2id output is normally stored as one string: $argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>. It holds the algorithm, version (19 = 0x13), the parameters, the salt and the digest, all base64 (salt and digest without padding). To verify, the library reads the parameters and salt from the string, hashes the entered password with them and compares the digests.

Comparison with conventional hashes

MD5 (128-bit) and SHA-1 (160-bit) are broken for collision resistance and are very fast. SHA-256 is secure as a general hash but still fast. PBKDF2 repeats HMAC many times, which adds CPU cost but not memory cost. Argon2id adds memory cost as well, which is why it is preferred for new systems.

Procedure

  1. Open the Simulation tab and type a password, for example correct horse battery staple.
  2. Click Random salt to generate a 16-byte salt (or type your own salt of at least 8 characters).
  3. Set the Argon2id parameters: memory cost (KiB), time cost (iterations) and parallelism. The defaults follow OWASP's minimum recommendation.
  4. Click Generate Argon2id hash. Read the encoded hash, its parsed fields, and the measured time. The run is added to the observation table.
  5. Watch the Memory fill visualizer: blue squares are the data-independent first half of pass 1, orange squares are data-dependent work, and later passes overwrite memory again.
  6. Change one parameter at a time (for example memory 4096 then 65536) and generate again. Compare the measured times in the observation table.
  7. In Verify password, enter the correct password and click Verify (MATCH), then a wrong password (NO MATCH).
  8. Click Run comparison to hash the same password with MD5, SHA-1, SHA-256, PBKDF2-SHA256 and Argon2id, and read the comparison table.
  9. Open the Quiz tab, answer all questions and submit to see your score.

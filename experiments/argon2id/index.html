Experiment Title

Brief description

Aim

To implement Argon2id for password hashing and compare its output and computational parameters with conventional hash functions (MD5, SHA-1, SHA-256, PBKDF2 and bcrypt).

Theory

A hash function converts a password into a fixed-length string called a digest. It is one-way, so the original password cannot be read back from the digest. A website stores only the digest. At login, it hashes the entered password and checks whether the two digests match.

Fast general-purpose hashes such as MD5, SHA-1 and SHA-256 were designed for speed. That is a weakness for passwords. Think of a fast hash as a rubber stamp: an attacker with a GPU can stamp billions of guesses every second and test them against a stolen database. Password hashing therefore needs a function that is deliberately slow and expensive.

A salt is a random value added to the password before hashing. Two users with the same password get different digests, and precomputed tables (rainbow tables) become useless. The salt is stored next to the hash and is not secret.

Argon2 won the Password Hashing Competition in 2015 and is standardised in RFC 9106. It is memory-hard: every hash needs a large block of RAM that must be filled and re-read many times. GPUs and custom chips have very little memory per core, so an attacker cannot run thousands of guesses in parallel cheaply. Argon2 has three variants. Argon2d is fast and resists GPU cracking but leaks timing information. Argon2i resists side-channel attacks but is weaker against GPUs. Argon2id combines both: the first pass behaves like Argon2i and the later passes behave like Argon2d. It is the recommended variant for password hashing.

Argon2id has three cost parameters. The memory size (m) is the RAM used in KB. The iterations (t) is the number of passes over that memory. The parallelism (p) is the number of lanes or threads. Raising m or t makes each guess slower for both the server and the attacker, so the values are chosen to keep login time acceptable, for example about 100 to 500 ms.

bcrypt is slow because of its cost factor but uses only about 4 KB of memory, so it is still weaker than Argon2id against GPUs. PBKDF2 is slow through many iterations but uses almost no memory.

Procedure

  1. Open the Simulation tab and type a password in the Password box. A sample password is already filled in.
  2. Set the Argon2id parameters using the Memory, Iterations and Parallelism sliders.
  3. Click "Hash with Argon2id". Note the encoded hash, which contains the parameters, the random salt and the digest, and note the time taken.
  4. Type the same password in the Verify box and click "Verify". The result should be a match. Change one character and verify again. The result should be no match.
  5. Click "Hash with Argon2id" again with the same password. Observe that the hash is different because a new random salt is used.
  6. Click "Compare with other hashes". Read the table for output size, time, guesses per second and time needed for one billion guesses.
  7. Increase Memory and Iterations and compare again. Observe that Argon2id becomes slower while MD5, SHA-1 and SHA-256 stay almost instant.

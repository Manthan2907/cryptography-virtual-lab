Relevant Theoretical Concepts

1. Background and The Password Hashing Competition

In modern computing, password authentication relies on cryptographic one-way functions to store credentials securely without keeping passwords in plaintext. Early authentication schemes used general-purpose cryptographic hash functions such as MD5, SHA-1, and SHA-256. While these primitives are secure for message integrity verification, their high computation speed and low memory footprint make them fundamentally dangerous for password hashing. A modern attacker with commodity GPUs or custom ASICs can compute hundreds of billions of SHA-256 candidate hashes per second, rendering brute-force and dictionary attacks trivially fast.

To address this vulnerability, the cryptographic community initiated the Password Hashing Competition (PHC) from 2013 to 2015. In July 2015, Argon2, designed by Alex Biryukov, Daniel Dinu, and Dmitry Khovratovich at the University of Luxembourg, was formally selected as the winner of the competition. Argon2 provides state-of-the-art protection against GPU-based password cracking, ASIC acceleration, and side-channel timing attacks, and is standardized in RFC 9106.

2. Memory-Hardness and Algorithmic Working Principle

Argon2 is a memory-hard function (MHF). An algorithm is considered memory-hard if evaluating it requires significant random-access memory (RAM) that cannot be traded away for computation time without exponential performance penalties. By filling a large matrix of memory blocks and referencing prior blocks iteratively, Argon2 forces an attacker with specialized hardware (ASICs or FPGA clusters) to allocate physical silicon memory for every concurrent attack lane, driving attacking hardware costs prohibitively high.

The execution pipeline of Argon2 operates in structured phases:

  1. Initialization ($H_0$): Variable-length inputs—password, salt, secret key, associated data, time cost $t$, memory cost $m$, parallelism $p$, and hash length—are compressed into an initial 64-byte digest using BLAKE2b.
  2. Memory Matrix Allocation: A 2D memory array of $p$ lanes and $q = \lfloor m / (4p) \rfloor \times 4$ columns of 1024-byte blocks is allocated in memory.
  3. Block Generation & Mixing: The first two columns of each lane are initialized using BLAKE2b. Subsequent blocks are computed using the compression function $G$, which operates on 1024-byte blocks using eight rounds of BLAKE2b's round function across rows and columns.
  4. Multi-Pass Iteration: The algorithm performs $t$ complete iteration passes over the memory matrix, overwriting and re-indexing blocks to prevent time-memory trade-off (TMTO) shortcuts.
  5. Final Tag Derivation: The final memory blocks from each lane are XORed and hashed with BLAKE2b to produce the derived output key or authentication tag.
Password + Salt + Parameters → Initial Digest ($H_0$) → Memory Matrix ($p \times q$) → $t$ Passes ($G$) → Encoded Hash

3. Important Cryptographic Parameters

M

Memory Cost (m)

Specifies the amount of RAM used in KiB (e.g., 65,536 KiB = 64 MiB). Increasing memory cost forces an attacker's hardware to dedicate physical memory for every parallel guess.

T

Time Cost (t)

Specifies the number of iteration passes over the memory matrix. Each additional pass re-reads and modifies all allocated memory, linearly increasing execution latency.

P

Parallelism (p)

Defines the number of independent execution lanes or threads. This allows multi-core systems to execute hashing concurrently without reducing memory-hardness.

4. Argon2 Variants Comparison

Variant Memory Access Pattern Primary Defense & Recommended Use Case
Argon2d Data-dependent indexing: prior block contents determine which memory address is accessed next. Maximizes resistance against GPU/ASIC parallel crackers and Time-Memory Trade-Off (TMTO) attacks. Vulnerable to side-channel cache attacks if running on untrusted shared hardware. Ideal for cryptocurrencies and proof-of-work.
Argon2i Data-independent indexing: memory access sequence is deterministic and pseudo-randomly scheduled. Immune to cache-timing and side-channel attacks because memory access patterns do not depend on the password secret. Slightly more susceptible to TMTO attacks than Argon2d. Preferred for password hashing in side-channel vulnerable environments.
Argon2id Hybrid mode: first half of the first pass uses data-independent indexing (Argon2i); remainder uses data-dependent indexing (Argon2d). Provides both side-channel resistance and strong TMTO defense against GPU acceleration. Officially recommended by RFC 9106 and OWASP for general password hashing and key derivation.

5. Encoded PHC String Anatomy

Argon2 encodes its output in the standardized Password Hashing Competition (PHC) serialized string format:

$argon2id$v=19$m=65536,t=3,p=1$<salt-base64>$<hash-base64>
  • argon2id: Specifies the algorithm variant used.
  • v=19: Specifies Argon2 version (0x13 = decimal 19).
  • m=65536,t=3,p=1: Explicit serialized parameters ensuring deterministic re-computation during verification.
  • <salt>: Base64-encoded cryptographically random 16-byte salt preventing rainbow table lookups.
  • <hash>: Base64-encoded derived output tag.

Step-by-Step Procedure

Follow these numbered steps to execute the Argon2 simulation and parameter analysis:

  1. Enter Password & Configure Input: Navigate to the Simulation tab. Enter a plaintext candidate password into the input field. Optionally toggle the "Show password" checkbox to verify masking behavior.
  2. Configure Cost Parameters: Select the desired Memory Cost ($m$), Time Cost ($t$), and Parallelism ($p$) using the interactive parameter dropdowns.
  3. Generate Triple-Variant Hashes: Click Generate All Argon2 Hashes. The WebAssembly engine compiles the password and generates Argon2i, Argon2d, and Argon2id simultaneously using the same cryptographically secure 16-byte random salt.
  4. Inspect Output Encodings & Telemetry: Observe the serialized RFC 9106 string outputs in each textarea and observe the elapsed execution latency measured in milliseconds.
  5. Verify Authentic Password: Scroll to the Password Verification card. Enter the authentic password and click Verify Password to observe constant-time validation success (✓ Password Verified).
  6. Test Mismatch Rejection: Enter an incorrect password and verify that the system rejects the credential securely (✗ Verification Failed) without leaking timing hints.
  7. Execute Parameter Benchmark: Scroll to the Parameter Analysis section. Choose custom memory, time, and parallelism configurations and click Run Benchmark to append timing telemetry to the observation table.
  8. Run Digital Test Suite: Switch to the Test Cases tab to run individual live assertions (TC01–TC12) or click Run All 12 Test Cases to validate full test suite compliance.
  9. Take Self-Assessment: Switch to the Assessment / Quiz tab, answer the 10 conceptual questions, and review detailed cryptographic feedback.

Key Learning Checks

Core Purpose of Argon2

Argon2 is an adaptive, memory-hard key derivation function engineered to protect passwords against mass parallel cracking on GPUs and custom ASICs.

Defense Against Side Channels

Argon2i uses data-independent indexing so memory access addresses never depend on password data, eliminating cache-timing leakage.

Hybrid Recommendation (RFC 9106)

Argon2id combines data-independent and data-dependent passes, offering simultaneous side-channel resistance and maximum TMTO defense.

Kerberos Authentication Protocol

Interactive step-by-step visualization of ticket-based authentication across Client Alice, Authentication Server (AS), Ticket Granting Server (TGS), and Server Identity Bob.

What is Kerberos?

Kerberos is a computer-network authentication protocol designed to allow individuals communicating over a non-secure network to prove their identity to one another in a secure manner. Named after Cerberus, the mythical three-headed watchdog of Hades, Kerberos relies on a trusted third party known as the Key Distribution Center (KDC) to facilitate mutual authentication between clients and network servers.

Why is Kerberos Used?

In traditional network systems, passing user passwords repeatedly across unencrypted connections exposes credentials to eavesdropping and replay attacks. Kerberos solves this through a ticket-based architecture:

  • Single Sign-On (SSO): Users authenticate only once with their password to get an initial ticket, after which they can access multiple network services without re-entering credentials.
  • No Password Transmission: Passwords are never sent over the network in plain text or hash form during routine service requests.
  • Mutual Authentication: Both the client and the Server Identity verify each other's identity before exchanging sensitive data.
  • Replay Protection: Timestamps and single-use authenticators ensure that captured tickets cannot be replayed by eavesdroppers at a later time.

Core Protocol Actors

1. Client (Alice)

The user or application requesting access to a network resource hosted on a remote server.

2. Authentication Server (AS)

Verifies the client's initial identity request and issues a Ticket Granting Ticket (TGT) encrypted with the client's secret key.

3. Ticket Granting Server (TGS)

Validates the client's TGT and issues a Service Ticket specific to the requested target server.

4. Server Identity (Bob)

The application or resource server (e.g. File Server) that validates the client's Service Ticket and grants access.

Key Cryptographic Tokens

  • TGT (Ticket Granting Ticket): A reusable token issued by the AS that proves the client has authenticated with the KDC. Encrypted with the TGS secret key so only TGS can read it.
  • Service Ticket (ST): A single-service token issued by the TGS that grants access to a specific Server Identity (Bob). Encrypted with the Server Identity's key.
  • Authenticator: A short-lived data structure containing the client's identity and current timestamp, encrypted with the session key shared between the client and server. Proves that the request is fresh and originates from the legitimate ticket owner.
  • Session Keys: Temporary symmetric keys generated by the KDC ($K_{c,tgs}$ for TGS communication, $K_{c,v}$ for Server Identity communication) to encrypt subsequent interactions.

The 6-Step Authentication Flow

The complete Kerberos protocol operates across three distinct request-response exchanges:

  1. AS-REQ: Alice sends her identity and a nonce to the Authentication Server (AS).
  2. AS-REP: The AS returns a TGT and session key $K_{c,tgs}$.
  3. TGS-REQ: Alice presents the TGT and an Authenticator to the Ticket Granting Server (TGS), asking to access Bob.
  4. TGS-REP: The TGS returns a Service Ticket and session key $K_{c,v}$.
  5. AP-REQ: Alice presents the Service Ticket and a fresh Authenticator to Bob.
  6. Verification: Bob validates the ticket, authenticator, and freshness (nonce/timestamp), completing mutual authentication.
